# AIBUS Partner workspace design

Audience: Indian travel-company developers, organization owners and finance readers integrating authorized AIBUS inventory. The main job is to understand sandbox readiness, provision reviewed access, inspect API contracts and diagnose owned requests.

Follow the existing AIBUS Admin product register: orange actions, cream canvas, warm white header, white bordered panels, compact tables and restrained spacing. The canonical runtime palette is `../admin/src/styles/theme.css`: accent `#c4522b`, hover `#a94322`, canvas `#faf7f2`, header `#fffdf9`, ink `#17201c`, focus `#2563eb`. The Partner entry imports that stylesheet directly. No independent token copy is maintained.

Inherit Arial for controls/headings and tabular numerals for operational metrics. Use Consolas/monospace for API request and response examples. The signature is a persistent, plain sandbox ribbon and a split endpoint explorer with the response status, duration and request ID alongside actual JSON. No decorative imagery, gradients or invented income.

The root owns the sidebar and document title. On narrow screens, navigation becomes a horizontally scrollable rail, endpoint columns stack, tables scroll inside panels and forms remain usable without page overflow. Shared Admin Panel, Overlay, PlatformTable and FinanceReviewForm own recurring behavior. PlatformTable's request adapter is the business variant for separate partner authentication; it does not create a second table implementation.

See `UX-CONTRACT.md` for workflow and verification. Browser screenshots are generated by `tests/isolated/partner.spec.ts` in `.cache`; they use disposable data and are not production screenshots.

Partner authentication uses a restrained two-column introduction/form layout at wide desktop sizes. Registration groups company and integration fields in two columns with full-width address, usage and password controls. Below 1000px the introduction is removed; below 540px fields stack. Existing brand tokens remain authoritative. Inline error summaries use clear semantic feedback, and password visibility is explicit. The onboarding sequence explains registration, review and sandbox access without suggesting automatic inventory approval.

The four developer sections use an API-reference register within the existing shell. Credentials explain generate/save/exchange, display status and human-readable IST timestamps; Inventory separates administrative grants from public trip references. DeveloperWorkspace owns grouped searchable method/path navigation, parameter and body tables, contract-derived cURL/JavaScript examples, OpenAPI download and the sandbox request/response explorer. `features/developer/developer.css` owns this layout and consumes the existing Admin tokens; no second theme is introduced. Green GET and amber POST labels encode HTTP methods alongside text. Code examples use the existing Consolas utility face and ink surface. Search stays visible in the endpoint scroller; request/response columns stack below 1250px and the endpoint rail stacks below 1000px.
