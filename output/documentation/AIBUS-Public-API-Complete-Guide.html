Current live availability

The Operator, Admin and Partner dashboards and backend are live. Production public booking token exchange currently returns 503 PUBLIC_API_DISABLED. The isolated Test API is active at https://partner.bookmybus.pro/api/v1/public and serves contract 1.0.0-test. Authentication and inventory were reverified over HTTPS on 21 November 2026. Actual hosted Razorpay checkout and ticket issuance still require acceptance testing. The new Partner Portal bridge is awaiting a reviewed release. A published API contract does not enable production booking sales.

Use this document to prepare access, import the supplied Postman files, run one dependent booking journey, inspect responses and return a reproducible report. All booking response examples are illustrative; no credentials, tokens or production passenger records are embedded.

Current City Master has 27,653 imported cities. Partner Cities responses are still restricted to authorized sellable trip inventory; they are not an export of the central catalog.

Owner prerequisite

Provision a separate sandbox database, server configuration and Redis namespace; approved sandbox partner; explicit inventory grants; active future test trip; test policies; and Razorpay Test Mode configuration. Do not point production at a sandbox database or disable its isolation guard.

Issue a dedicated, expiring credential to each external tester. Share the collection and blank-secret environment as files, and send the individual credential through an agreed private channel. The owner should confirm the test window and revoke access when testing is complete.

The public API is server-to-server. Postman must not send browser Origin or Cookie headers. Full API credentials belong in trusted backend tooling, never in a customer-facing frontend application.

The server derives the partner identity and inventory grants from the credential/token. Client-supplied operatorId or agentId never grants access. External API partners are separate from operator-owned travel agencies.

Only a successful current hold owns a seat. Booked or blocked seats cannot be sold by requesting their number. Expired or replaced ownership cannot authorize a late confirmation. Final booking and test financial transitions are protected by the central MongoDB reservation logic.

Three different outcomes

Pending booking is not paid. Confirmed sandbox booking is simulated, not a live travel ticket. Requested cancellation is a review request, not a completed refund.

Run dependent requests sequentially. This collection is not a load or concurrency test; dedicated integration regressions cover competing reservations, duplicate confirmation and late-payment recovery.

Holds, booking creation, payment creation, payment verification, payment reconciliation and cancellation each require a different Idempotency-Key header. Keys are partner-global, payload-bound, 16-100 characters, using letters, digits, underscore, dot, colon or hyphen. A key must not be reused for a different action or changed payload.

Idempotency-Key: postman-example-20301120-01-hold
Idempotency-Key: postman-example-20301120-01-booking
Idempotency-Key: postman-example-20301120-01-payment

After a timeout, retain the exact body, key and partnerReference and inspect existing booking status. Token refresh must preserve these identities. Start a new testRunId only after resolving the previous outcome. The collection retains the previous booking ID when starting a new independent run.

Do not manually overwrite server-calculated totals, claim paid:true, forge a payment reference or use another partner's IDs. Each request remains server-authorized.

Passenger and booking payload reference

Use the exact public IDs returned to this partner. Hold and quote IDs must belong to the same trip and current reservation; copying another provider's IDs or typing placeholders will fail validation.

passengers[].phoneOptional phone matching ^\+?[\d\s-]{10,16}$.
passengers[].emailOptional valid email, at most 254 characters.
passengers[].boarding / droppingOptional, at most 200 characters; if supplied, use the configured route stop name exactly.

Runtime validation detail

The generated OpenAPI contact object may appear to have optional members. The current runtime requires phone whenever a contact object is included. Include a valid synthetic phone, or omit contact entirely when the quote does not require mobile.

The public booking body is strict. Do not add arbitrary operatorId, agentId, paid, totals, payment credentials or a gst object. A quote reporting gstEnabled does not introduce a public GST submission field. Use only documented public fields.

Examples use synthetic contact details. Store actual passenger information only in authorized systems; redact names, phone numbers, emails, credentials and tokens from shared test reports.

Signed webhook receiver requirements

The owner provisions sandbox webhook subscriptions through trusted server administration. HTTPS destinations must be explicitly allowlisted and publicly routable. The API does not expose a public callback-registration endpoint in this collection.

HeaderMeaning
X-Aibus-Event-IDStable event identity for durable deduplication
X-Aibus-TimestampEpoch milliseconds for replay-window validation
X-Aibus-SignatureHex HMAC-SHA256 of the signed input
signedInput = timestamp + "." + eventId + "." + rawBody
expectedSignature = HMAC_SHA256(subscriptionSecret, signedInput)

Verify the exact raw request bytes before parsing JSON, validate a five-minute timestamp window, compare signatures in constant time and durably deduplicate event IDs. Persist receipt before acknowledging the event. A valid signature alone does not prevent replay inside the allowed window.

Delivery is at least once. Retries preserve event identity with fresh timestamps/signatures, use bounded backoff and stop after five failed attempts in Manual review. A timeout may mean the receiver accepted the event. Retrying a notification must never repeat booking confirmation or a refund.

The delivery-history endpoint shows attempts and status. Verify reception using a trusted mock receiver or your actual allowlisted endpoint; an empty history response is not delivery evidence.
