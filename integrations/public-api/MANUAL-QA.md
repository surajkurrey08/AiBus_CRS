# Reproducible acceptance checks — public API sandbox

Use the isolated non-production environment and guide in README.md. Never use real passenger details or point the fixture CLI at an ordinary/production CRS database. Configure Razorpay Test Mode only. No real charges, live refunds or bank payouts are part of these checks.

1. Run the read-only preflight; review uniqueness/conflicts. Prepare the separately named MongoDB replica set and explicit sandbox environment. An ordinary database must return PUBLIC_API_DISABLED even with valid sandbox credentials.
2. Create the additive sandbox fixture. Keep its one-time credential on your backend. A repeat fixture run must preserve records and not print the old credential again.
3. Exchange the credential; verify 45-minute token lifetime. Revoke it, expire it or increment its version in an isolated integration fixture: the old token must fail. A dashboard JWT must not authenticate the public namespace and vice versa.
4. Provision two separate partners with only explicit sandbox trip grants. Remove/expire Partner A's grant: it must not discover or sell Partner B-only inventory. Operator/agent IDs in public query/body must be rejected, never treated as authorization.
5. Get cities, then search with returned IDs and the exact fixture date. The other date should return no trips. Compare seat/deck positions with the central sandbox inventory and verify no hold-user, booking database ID, crew contact or credential appears in JSON/JWT claims.
6. The available fixture has green/sellable availability; the blocked fixture has zero available seats. Its unavailable seats must not be held. This is a deliberately blocked availability scenario, not invented booked passengers.
7. Quote a seat, hold it with a stable request key, then recheck with its hold ID. Verify final quote equals configured integer-paise price/tax/fees. A quote without hold binding must not authorize a booking. Change a fare through an authorized sandbox fixture/workflow: stale hold/quote booking must fail without creating a ticket.
8. Repeat/concurrently submit the identical hold request/key: one central hold identity must result. Change seats under that key: conflict. Compete through the public and operator reservation service: only one may own the seat.
9. Let the five-minute hold expire (or use the deterministic disposable regression fixture). Have another partner hold the seat before cleanup. Old request replay, late confirmation and expiry cleanup must leave the replacement ownership intact.
10. Create a pending booking with a stable key and partnerReference; repeat after simulating a lost response. The same public/central reference must return, without another booking. A different payload or re-bound reference must conflict.
11. A `paid:true`, arbitrary amount or unsupported authorization claim must fail. Payment order creation must use the stored CRS booking total and Razorpay Test Mode. A valid test checkout signature plus provider-side captured state may confirm the booking once, post balanced central ledger entries and issue one ticket/PNR. Invalid signatures, mismatched order/amount/currency and expired seat ownership must not create a valid ticket; late captures must enter reconciliation.
12. Retrieve the own ticket/status. Another partner must receive 404 for that ID, ticket, cancellation quote/request and refund evidence. Ticket response may contain authorized names/seats; status/search/notification responses must not include passenger contact dumps.
13. Request a cancellation quote with the explicit sample accounting policy, then submit a full cancellation request twice with the same key. One request must exist; seats remain booked until the existing operator review accepts it. Only after approval may the refund worker submit/reconcile a Razorpay Test Mode refund. Partner refund status must remain pending/uncertain until verified provider evidence is recorded. No partner API endpoint may approve a cancellation or initiate a refund/payout.
14. Reschedule and partner wallet must return documented unavailable responses (501 in an enabled sandbox). An agent wallet must never appear as a partner balance.
15. Use only a trusted allowlisted HTTPS mock receiver for notifications. Verify raw-body signature, timestamp and stable event identity; persist deduplication at the receiver. Simulate timeout after acceptance, non-2xx and worker restart. Retry must preserve event identity and never repeat confirmation/refund. Five failures must end in Manual review with durable attempt history. Private/link-local/rebinding/redirect destinations must be denied. Default unconfigured signing/host settings must cause no external delivery.
16. Run `npm.cmd run test:e2e:isolated` for the four actual browser smoke checks with separate local ports and disposable Redis/MongoDB. The wrapper requires Docker access and installed system Chrome. It verifies run labels before cleanup. No existing server reuse or personal credentials are allowed.

Automated reproduction: `npm.cmd run test -w backend -- tests/integration/public-api.test.ts tests/integration/operations.test.ts`, followed by the full workspace suite. The deterministic tests mock Razorpay HTTP and use disposable MongoDB fixtures; they do not call the real provider.

Browser work still outstanding: complete interactive booking search/selection/passenger/payment/PNR/cancellation flow, all master creation/scheduling flows, passenger check-in, cross-tenant UI actions and session-expiry handling. Existing root `tests/e2e` placeholders/default ports are not evidence those flows pass. Public APIs are server-to-server; never move a partner credential into browser code just to exercise them through a UI.
