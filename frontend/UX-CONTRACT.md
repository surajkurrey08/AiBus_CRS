# UI contract

Area Master is an operator section with tenant-owned cities, pickup/drop/both locations and POI/landmarks. Native selectors link locations and POI to cities. Route stop assignment selects exact origin/destination city IDs, ordered points and route-specific IST times. Server validation rejects foreign, inactive, wrong-city and wrong-usage points, duplicate selections and stale route versions. Legacy text-only route stops remain supported. Linked stops resolve current active master names/addresses in counter search and passenger validation, while saved passenger boarding/drop strings remain booking records. Route forms offer active city-name suggestions. Master lists reuse DataTable, editing/details reuse Overlay, and all writes require routes permission. Shared paginated option loading lives in src/api/loadAll.ts. One-hop connecting booking behavior is outside this module.

Bus Master is an operator workspace section backed by tenant-scoped `/operator/bus-master` APIs. It owns reusable seat charts, coach types, owners, crew, vehicle document/service dates and GPS device configuration. Its Vehicles tab owns bus records, add/edit actions, fleet totals, owner/coach assignment and seat layout/image configuration. The separate Fleet screen is removed. Templates are applied only to matching-capacity buses and affect newly scheduled trips. Charts share the seat-layout builder and SeatMap preview with the bus configuration workflow. Master lists reuse DataTable with server search/pagination, forms reuse Overlay and native controls, and mutations require fleet permission. Optional driver/conductor/pickup crew selection is available during scheduling and for existing scheduled trips. The server checks driver licence expiry and uses shared crew writes to reject simultaneous overlapping assignments. GPS status explicitly reports missing telemetry until an actual provider adapter is connected.

Schedule a trip also accepts optional double-side (2) and single-side (1) prices per person from pricing-authorized users. Both prices must be positive INR amounts with at most two decimals. These trip-specific prices override all route/date/seat defaults for that trip; both decks use the same side rule, and seater positions use the double-side rate. Omitting both prices retains existing route pricing. Scheduling validates and snapshots integer paise, stores the supplied prices for traceability, and never edits route fares or earlier trips. Switching bus or route clears the custom-price draft.

Fares tab owns pricing: the route fare form sets double-side and single-side rates per person separately for weekdays and weekends. For 2+1 sleeper rows, adjacent berths use the double-side rate and the berth across the aisle (column 3) uses the single-side rate on both decks. Seater decks use the double-side/base rate. Backend scheduling snapshots the route rates in integer paise, with existing seat overrides and special-date rates taking priority. Legacy fare records without single-side fields retain their previous base/weekend behavior. LayoutEditor configures positions only, preserves existing per-seat fallback fares and uses zero for unpriced new seats. Scheduling rejects unpriced seats and directs the operator to Fares. Existing trips and quotes keep their snapshots; changing route fares affects newly scheduled trips only.

Razorpay Test Mode is available for configured internal trips. Payment actions appear after saving a pending booking and in saved-booking details. React opens the provider's hosted Checkout with the server order, then sends only the signature proof for backend verification. The app's native dialog is temporarily closed/restored around hosted Checkout so it cannot block the payment UI. Only captured, order/amount/currency-bound payments with valid seat ownership produce confirmation. Closing Checkout, a client success callback or an unknown network outcome alone cannot mark a booking paid. Test Mode is visibly labeled; live keys and automatic refunds are unavailable. See ../backend/RAZORPAY.md.

Live New booking actions navigate to Booking Counter instead of the simplified demo form. The hold action lives next to the fare grid. Successful holds focus and reveal the booking-contact field; validation errors also appear in the passenger panel. The explicit demo form remains isolated to UI fixtures. Creating a pending record is distinct from payment confirmation and ticket issuance.

Booking counter defaults to booking mode: only available seats can be selected. Booked seats remain disabled. Blocked/quota seats are selectable only in the explicit inventory-management mode for release operations, and cannot be quoted/held for booking. Hold handlers require an all-available selection; the server's atomic availability predicate independently rejects blocked/booked seats. Available seats are green on both decks; booked and blocked seats are red, including blocked seats selected for management.

Shared visual owner: src/styles/theme.css owns all twelve operator pages, authentication forms and portal dialogs. Counter-specific chart and fare layouts remain in counter-crs.css. Icon navigation retains accessible names and native title tooltips. Native form controls, permissions, validation, confirmations, async recovery and booking semantics remain unchanged. Documents scroll naturally; tables keep their own horizontal overflow.

Sources: supplied Aibus operator frontend and backend briefs; architecture is documented in ../ARCHITECTURE.md. Default runtime uses the authenticated operator API; fixture mode is explicit in tests.

Seat blocking/release is performed atomically by backend inventory services. Holds expire after five minutes by database predicates. Only the authoritative booking/payment flow can issue tickets. Refund completion is unavailable until verified adapters exist. E-ticket printing rechecks confirmation with the API. CSV respects server-side filters and permissions. Company settings and staff permissions persist in MongoDB; tokens and passenger records are not stored in localStorage. Native select/date geometry remains intentional. Errors never switch the application to sample data. Super-admin approvals use the separate platform API.

## Counter ownership

- SeatMap is shared by Booking Counter and live seat inventory; row, column, deck and fare come from the trip snapshot. Quota assignment/release uses the existing Trip inventory document.
- SeatMap's counter-chart variant renders both decks together, offsets upper-deck columns after the lower deck, and retains each seat's original coordinates and accessible state. The default inventory variant retains keyboard deck tabs. Counter fare-grid outputs are read-only server quote values; selecting a seat never constitutes confirmation. Origin/destination swap only changes the uncommitted search fields and is disabled while seats are held.
- features/booking-counter/api/counter.api.ts owns counter endpoint contracts; features/booking-counter/components/CounterDialogs.tsx owns reusable passenger fields and confirmation/details dialogs. Existing Overlay now portals its native dialog to the document body so print views and focus isolation work consistently.
- Counter search is explicitly submitted and stale responses are cancelled. Seat/quote/passenger drafts are intentionally transient and excluded from URL/localStorage because they are operational or personal data.
- Quotes expire, bind to an authenticated user's hold, and are recomputed on booking creation. Operator discounts need permission and a configured limit. Policy edits use version checks. Tax rates are never assumed.
- Booking creation uses a stable idempotency key and immutable retry payload when its outcome is uncertain. Recovering the request cannot create another booking. An unpaid pending cancellation releases only seats still belonging to that booking.
- Block/quota/stop/cancel actions use the shared confirmation dialog. Leaving with a hold or unsaved passenger details asks for review. Server permissions always govern mutations and passenger/payment visibility.
- External booking and live-payment confirmation remain unavailable. Configured Razorpay Test Mode can confirm internal bookings only after verified capture; pending records cannot print or download a valid ticket.

Counter search is submit-only: mounting the page never searches or selects a trip. Origin, destination and journey date are required. A new submitted search clears the previous trip, selected seats and result list before loading results, so errors or no-matches cannot retain the previous route's chart. Background inventory refresh starts only after a trip has been selected from submitted results and reuses the committed route/date.

## Trip Master

The Trip Master sidebar entry extends the same warm Aibus theme, shared DataTable search/filter/export, Overlay dialogs and native date/time controls. Its workflow is Services → Multi-trip scheduling → Service availability → Trip tracker. Times are labelled IST; money is entered in INR and stored as integer paise. Separate double/single side fares are per passenger.

Service changes affect future trips; dated trip inventories remain snapshots. Bulk scheduling has an explicit preview, invalidates previews when inputs change, revalidates on save and rolls back the batch on conflicts. Existing service/date trips are skipped. Single-trip scheduling supports an optional recurring service with explicit bus, fare and crew overrides.

Operational stages are sequential and version checked. Actual times, odometers and measured fuel consumption drive reports; unavailable measurements say Not recorded. Fuel purchases are separate from fuel consumption. GPS and Revmax show Not connected/not configured until an actual provider is integrated. Connecting trip links are metadata and do not promise combined ticketing.

Agents/branches are optional referrals in the counter. Commission is calculated on the server and snapshotted into bookings; it never changes the passenger total or frontend-controlled booking source. Default basis is fare after discounts before tax/charges; trip rules override service rules. Fuel writes and tablet mutations are audited. Fuel/stop submissions and operational events use stable idempotency keys for retries.

Sidebar navigation keeps one Master button in the compact rail. It navigates to a dedicated Master page with three responsive icon/name/description cards: Bus Master, Area Master and Trip Master. Choosing a card opens its module through the existing navigation guard. Each child module has an All masters breadcrumb link back to the hub. Master uses normal page selection semantics rather than a dialog or disclosure. Hiding the sidebar still hides the entire rail.


Navigation consolidation: Master is the sole entry for setup. Bus Master owns vehicles and fleet configuration; Area Master owns locations; Trip Master owns Routes, Scheduled trips/calendar, Services and the existing operational tabs. Fleet and Routes are removed from the sidebar, and their standalone page bodies are removed. Existing Overview quick actions redirect to the owning Master (route/departure shortcuts open Scheduled trips). Seats remains trip-specific inventory management; Counter remains passenger booking and payment. The same APIs and records are reused; no data migration is involved.


Master sections share components/navigation/MasterSectionLayout.tsx. Desktop uses grouped vertical tabs beside the content panel, with a consistent selected state and no joined top-tab strip. Bus Master groups Bus setup, People, Vehicle records and Trip assignment; Area Master groups Location setup and Route mapping; Trip Master groups Planning, Operations and Business. At widths up to 950px, a labelled native section select replaces the side navigation. Selection stays synchronized, vertical tabs support Up/Down/Home/End, and each selected tab is linked to its content panel.

## Operator-owned agencies

SalesPartner Agent records are canonical; a booking staff user is internal until explicitly linked. Agent reports require agents:read; mutations require agents:write. Render loading, Retry on error, empty lists, create/edit, permissions, status, login linking and booking history explicitly. Never fabricate sales after API failure. Enter INR/percent and send integer paise/basis points; preserve zero and historical snapshots. Earned commission excludes unpaid/cancelled/refunded records. Reuse shared table, overlay, form and notification owners; selects retain native platform popup behaviour. Validate with associated errors and focus, prevent duplicate submits, retain failed drafts, confirm discarding agency edits, and ignore stale list/detail responses. Agents cannot enter operator management; customers are not permanently agency-owned. Agency settlement is owned by the separate Finance workflow; live payouts remain unavailable.

## Finance controls

Source: ../backend/FINANCE-PHASES.md and finance API ownership checks. Finance is permission-gated and reuses Panel/DataTable/Overlay. FinanceActionForm owns financial review, integer-paise INR entry, stable operation identity across uncertain retries, retained errors/drafts and discard confirmation. Finance list search/status/paging is server-owned. Detail requests abort/ignore stale results and clear old financial summaries before loading. Test funding is visibly distinct from live funds. Commission is not added to spendable balances. Date-bound statements enforce server ownership and export limits. Missing indexes/policies/permissions remain explicit failures, never fixture fallbacks. No unrelated navigation or Master/Counter workflow is redesigned.

Financial reporting uses server-filtered date/scope/status/search queries, pagination, explicit report generation and protected CSV export. Outstanding balances are as of the period end. Settlement cancellation after a payable claim fails closed until an approved compensating workflow exists. Financial labels must retain TEST markers, independent approval and original evidence links; a processed test payout never implies a bank transfer.
